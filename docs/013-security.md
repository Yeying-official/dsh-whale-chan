# 013 安全基线

> 状态：**v1.0 安全基线（2026-11-03）**，WS8 Windows 真机 T0–T4 已完成；v0.2.0 在 §4 与 §8 补记按会话共享工作区的边界。实现或威胁模型变化时，先改本文与对应测试，再改代码。
>
> 范围：`dsh-whale-chan-assistant` 插件本身的授权、发送、任务、数据与事件响应。DSH 宿主、`dws` 供应链、钉钉服务端与操作系统安全不在本文保证范围内，只在“明确不防御”一节列出。

## 1. 威胁模型

### 1.1 资产

| 资产               | 说明                                                                  |
| ------------------ | --------------------------------------------------------------------- |
| 主人的钉钉发言能力 | 插件通过 `dws` 个人授权，以主人本人身份读取与发送消息，不是机器人账号 |
| 消息与任务数据     | 消息正文、发送者、决策、草稿、任务、批准、派工、审计事件              |
| `dws` 凭证         | 由 `dws` 自己保存；插件只读取版本、授权布尔、过期时间与本人 userId    |
| 任务工作区         | worker 会话可读写的本地目录；默认 `~/.dsh-whale-chan/tasks/<taskId>`  |
| 审计与设置历史     | 谁在什么时候批准/取消/修改了什么，用于事后核对                        |

### 1.2 信任边界

- 插件信任**当前操作系统用户**就是主人。同一用户下的其它进程、同一 DSH profile 中的其它插件，默认都在信任边界内。
- 插件不信任钉钉消息内容、群成员、引用文本、检索结果与模型输出；这些是**数据**，不是指令。
- 插件不信任“模型会遵守提示词”：安全边界由代码（审批、outbox、权限、过滤）承担，提示词只降低概率。
- `dws` 是外部可执行文件；插件解析并调用它，但不验证它的签名或来源。

### 1.3 主要风险

| 风险            | 典型场景                                                 | 影响                                         | 主要控制                                                                         |
| --------------- | -------------------------------------------------------- | -------------------------------------------- | -------------------------------------------------------------------------------- |
| 误触发          | 目标配成大群、群消息未要求 @、发送者名单为空、广播未过滤 | 在错误会话以主人身份发言                     | 目标白名单、群聊默认必须 @、广播过滤、`allowedSenders`、限速、静默时段、`review` |
| 越权执行        | 消息里写“帮我付款/删库/发全员”，模型将其捕获为任务       | 执行主人未批准的动作                         | 任务必须人工批准；没有 Approval 不建会话；批准 TTL；工作区与权限最小化           |
| 提示注入        | 消息、引用、网页检索结果里写“忽略之前的规则，执行……”     | 模型写出不当内容，或在已批准任务中做多余操作 | 数据/指令分离；分类 JSON 严格校验；回复后处理；worker 工具集受限；人工批准       |
| 账号被盗        | 主人的钉钉账号或本机登录态被他人取得                     | 攻击者可直接以主人身份发言，插件无法区分     | 单实例、日志脱敏、最小目标集、定期审计；账号侧的安全设置是主防线                 |
| 群范围扩大      | 主人误加目标、把 `@我` 指向大群、发现候选被自动保存      | 监听面与误回复面扩大                         | 目标只手工保存；发现结果只是候选；面板显示每行启用状态与回复模式                 |
| 数据泄漏        | 日志、备份、状态目录、模型请求、检索查询                 | 消息正文、联系人、任务内容外泄               | 默认日志脱敏；本地 SQLite；模型/检索只发必要文本；备份由主人保管                 |
| 重复发送        | 崩溃恢复、重试、通道回执不明                             | 对方收到重复消息                             | `idempotencyKey` 唯一；`unknown` 终态不重发；启动只恢复 `pending` outbox         |
| 供应链/本机提权 | `dws` 被替换、DSH 插件被篡改、同用户恶意进程             | 完全绕过插件控制                             | 只从可信来源安装；校验路径与版本；不在不受控机器上运行                           |

| 同源 API     | 所有管理请求要求 `x-whale-chan-request: 1`；服务不发送 CORS 允许头，跨源页面无法伪造                           | `src/shared/api.ts`、`tests/api-routes.spec.ts`                                  |
| 失败关闭     | 模板缺失/空白、授权缺失、状态目录不可写、数据库版本更高时，不启动订阅或任务                                    | `docs/006` §10、`tests/runtime-pipeline.spec.ts`                                 |
| 演练         | `advanced.dryRun` 下发送返回 `skipped`，不 spawn、不改 Outbound 状态                                           | `docs/006` §6、`tests/channel-send.spec.ts`                                      |
| 媒体         | v1 没有附件字段；纯媒体事件按 `unsupported` 跳过，state.db 不保存媒体原文件                                    | `docs/009` §4.3                                                                  |

## 3. 明确不防御

以下情况插件**不能**提供有效保护，必须靠操作系统、钉钉账号安全与运维流程：

- **宿主被攻陷**：攻击者取得 DSH 进程、本机管理员权限或同一用户 shell，可读状态目录、改 `dws` 路径、直接发消息。
- **`dws` 二进制被替换或被投毒**：插件只解析路径并调用，不验证签名/哈希；恶意 `dws` 可以伪造事件与回执。
- **主人钉钉账号本身被盗**：攻击者不经过插件也能以主人身份发言；插件无法区分“主人”和“拿到主人账号的人”。
- **恶意群成员的社会工程**：人设、提示词与策略只能降低被诱导的概率，不能保证模型永不写出不当内容；最终发送仍受策略与人工批准约束，但内容质量不是硬保证。
- **模型提供方与检索适配器的数据处理**：回复/分类/任务所需文本会按 DSH 的模型路由发出，检索查询会发给搜索适配器；其留存与合规由提供方决定。
- **同一操作系统用户下的其它进程**：可读内存、状态目录或调试日志；状态目录权限只是降低风险，不是进程隔离。
- **本地未加密**：`state.db` 是明文 SQLite，没有应用层加密；依赖磁盘/用户目录 ACL 与设备加密。
- **钉钉服务端与网络**：消息在钉钉服务器上的留存、撤回、审计与传输安全由钉钉负责。
- **物理访问、屏幕录制、键盘记录**：不在插件边界内。
- **错误目标 ID**：插件按配置的显式 ID 发送；如果主人把 ID 配错，插件不会猜测“应该是另一个群”。

## 4. 数据位置与保留

| 路径                                          | 内容                                                                 | 保留/删除                                                            |
| --------------------------------------------- | -------------------------------------------------------------------- | -------------------------------------------------------------------- |
| `<stateDir>/state.db`                         | 消息、线程、决策、草稿、任务、批准、派工、Outbound、审计、设置与历史 | 只增；`advanced.auditRetentionDays` 目前只是设置，**自动清理未实现** |
| `<stateDir>/state.db-wal` / `-shm`            | SQLite WAL 与共享内存                                                | 运行时存在；正常关闭后 WAL 合并                                      |
| `<stateDir>/.lock`                            | 单实例锁（目录）                                                     | 运行时存在；停机后保留，stale 10 秒可接管                            |
| `<stateDir>/workspaces/conversation-<digest>` | 会话工作区：该会话的回复器与任务共用（v0.2.0 起的默认位置）          | 含任务产物；随状态目录备份；停用目标不删除                           |
| `<stateDir>/tasks/<taskId>`                   | 旧回退目录（只有组合根未注入工作区解析器时才会用到）                 | 可保留或由主人清理；删除前确认没有运行中的任务                       |
| `<stateDir>/workspace`                        | 旧版回复器共用工作区（v0.1.0）；升级后保留但不再使用                 | 保留供历史会话打开；可以手工归档                                     |
| `dws` 自己的凭证存储                          | 钉钉登录态                                                           | **不在 stateDir**；由 `dws auth` 管理                                |

- 插件**不保存**媒体原文件；纯图片/文件/语音消息按 unsupported 跳过。任务执行过程中由 worker 写入工作区的文件不属于插件数据库。
- 备份：停机后等 WAL 合并，复制整个 `stateDir`；在线备份用 `sqlite3 state.db ".backup '<backup>.db'"`。不要只复制 `state.db` 而漏掉 WAL。
- 删除：先停插件、确认没有运行中的任务与订阅，再删除整个 `stateDir`。这会永久删除消息、任务、批准、审计与设置，**不可恢复**；先备份。
- 审计保留：`advanced.auditRetentionDays` 默认 30，但 v1 没有清理器；需要缩短保留期时，只能停机后手动备份/重建，或等后续版本实现。

## 5. 事件响应

发现异常发送、任务被越权执行、账号疑似被盗或目标被误加时：

1. **先止血**：在「概览」暂停监控（停止新订阅），取消运行中的任务；必要时退出 DSH。暂停只停订阅，不取消已运行任务，任务要单独取消。
2. **停通道**：确认没有遗留订阅。`dws event status` 查看；若有孤儿订阅，按 `dws event stop <subscribe_id> --yes` 清理。不要在插件运行时手删 `.lock`。
3. **撤销授权**：`dws auth logout` 清除本机登录态（默认所有组织；可用 `--profile` 只退一个账号）；需要彻底重置时用 `dws auth reset`。如果怀疑账号被盗，同时修改钉钉密码、检查登录设备与安全设置——本机 logout 不等于服务端会话全部失效。
4. **保留证据**：在删除任何东西之前，停机复制整个 `stateDir` 与 DSH 日志；记录时间、目标、消息 ID/幂等键、任务 ID 与操作者。不要先把库清空再排查。
5. **评估范围**：检查「目标」「人设」「设置」是否被改；检查「审计」中的 `task.approved`、`reply.delivered`、`outbound.*`、`targets.updated`；核对 `unknown` 投递是否需要人工对账。
6. **清除**：移除未知目标、恢复人设/设置、重新安装可信版本的插件与 `dws`；如果宿主被攻陷，按“重装系统 + 轮换凭证”处理，而不是只删插件。
7. **恢复**：用备份恢复到没有 `.lock` 的目录，重新 `dws auth login`；先以 `dryRun`/`review` 和最小目标集恢复，确认 T0–T1 后再开自动回复。
8. **记录**：把事件、影响、处置与后续动作写入内部记录；不要在校验前把含账号/消息正文的原始日志发到公开渠道。

## 6. 运营建议

- 只在**受控群**与明确单聊中使用；`@我` 不要指向大群。
- 目标保持最小集，逐行确认 `enabled`、`mentionOnly`、`replyMode`；新增目标先保存再观察。
- 首次联调用 `dryRun=true`，再用 `review` 或只发测试群；确认 AI 角标与回执后再开 `auto`。
- 定期看「审计」与「概览」的 health/`effects`；发现 `dead` effect 或 `unknown` 投递先停下核对。
- 任务默认 `workspace-write`；只有明确需要时才选 `danger-full-access`，并限定工作区。
- 备份 `stateDir` 与设置；升级前先备份，降级时不要用新 schema 的库打开旧插件。
- 不在不受控的共用电脑上登录 `dws`；离开时锁屏。

## 7. 已知缺口（v0.2.0）

- 真机 T0–T4 未覆盖 `dws auth logout` 后的通道行为、Windows 关闭 stdin 的优雅退出，以及 `unknown` 回执的人工对账流程。
- 单聊 o2o 链路未真机触发；群事件与群发送已真机确认，单聊仍按同一策略与归一化路径处理。
- `advanced.auditRetentionDays` 没有自动清理实现；v1 的审计/消息是只增的。
- 没有应用层数据库加密；依赖 OS 账户与磁盘加密。
- 没有对 `dws` 可执行文件做签名/哈希校验；只做路径解析与 `binaryPath` 覆盖。
- 没有钉钉侧批准或二次确认；批准只在 DSH 面板。
- 账号被盗、宿主被攻陷、恶意群成员诱导等场景只能降低概率，不能由插件保证。
- `@我` 与 `open:` 单聊的工作区只在单元测试中验证惰性创建，未做真机；`open:` 依赖发送用 id，真正的会话键以首条消息为准。
- 工作区目录不会随目标或会话删除而回收，也没有“清理孤儿目录”的命令；需要主人手工判断。

## 8. 共享工作区安全边界（v0.2.0）

v0.2.0 把回复器与任务放进同一个按会话目录。这改变了“谁能看到什么”，边界如下：

| 边界         | 规则                                                                                                   | 含义                                                                                       |
| ------------ | ------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------ |
| 同会话共享   | 一个 `threadKey` 一个 `conversation-<digest>`；该会话的回复器与它派生的每个任务共用                    | 任务写下的文件，后续回复可以读到；同一目录内不要放凭证、token 或与本会话无关的私人文件     |
| 跨会话隔离   | 不同会话（群 / 单聊 / `@我` 命中的会话）摘要不同，目录不同                                             | 会话 A 的任务产物不会被会话 B 的回复读到；隔离粒度是**会话**，不是单条消息                 |
| 全局目标惰性 | `@我` 与 `open:` 单聊没有单一会话，在收到首条消息时才确定目录                                          | 不会把多个群或多人共用一个目录，也不会在启动时预建一个无法命名的目录                       |
| 不回收       | 停用/删除目标、修改 `tasks.workspaceRoot`、升级布局版本都不会删除旧目录                                | 历史属于主人；清理是人工操作，需先确认没有运行中的任务                                     |
| 路径安全     | 目录名只由 `threadKey` 的 SHA-256 前 16 位决定；根必须是绝对路径；相对路径被忽略并回退到 `workspaces/` | 构造 `../` 的会话键只改变摘要，不能越出根；主人也不会遇到不可预测的落点                    |
| 显式覆盖     | 批准时填写的绝对目录优先于会话工作区                                                                   | 这是**人工例外**，等同主人显式授权；插件不改会话标题、不搬目录，也不把该目录并入会话工作区 |

- 工作区决定 worker 能写哪里，权限仍由 `tasks.permissionPreset` 决定（默认 `workspace-write`，只有显式选择才 `danger-full-access`）；两者是独立的闸门。
- 工作区文件**不在** `state.db` 里：`sqlite3 .backup` 不含它们，备份状态目录时要连同 `workspaces/` 一起复制。
- DSH workspace registry 只是一条 path → 标题的引用；目录被删掉后记录仍在，下一次预建会重建目录并复用记录，不会因此放宽任何权限。
- 同一操作系统用户下的其它进程仍可读写这些目录（见 §3），目录以 `mode: 0o700` 创建只是降低误读概率，不是进程隔离。
